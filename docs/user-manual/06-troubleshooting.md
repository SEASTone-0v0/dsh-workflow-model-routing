# 第七章　保存全部草稿、冲突处理与故障排查

## 7.1 “保存全部草稿”实际保存什么

按钮显示为“保存全部草稿（N）”。N 由未保存的模式数量和待同步的全局授权/全局角色状态组成，不是将要生成的模型请求数，也不代表 N 个模式会被启用。

它按顺序处理：

1. 逐个保存有未保存修改的模式；单项失败后继续尝试其他模式。
2. 如果授权有变化、全局同步仍待完成，或当前模式本身有修改，再保存一次全局角色与授权。
3. 最后汇总失败数量；全部成功才显示完成。

**它不是事务。** 可能出现：

- 模式 A 已保存，模式 B 冲突失败；
- 模式草稿已保存，全局授权/角色保存失败；
- 某些模式保存成功，但当前模式仍处于冲突或未保存状态；
- 授权已更新，而某个引用它的模式草稿尚未保存成功。

因此“部分完成”必须逐项核对，不能把按钮恢复可点击理解为全部一致。

## 7.2 推荐的保存顺序

### 只改当前模式

1. 在底部点击“保存设置”。
2. 检查顶部不再显示当前模式有未保存修改。
3. 如需切换运行状态，再点击“启用此模式”。

### 同时改了多个模式或授权

1. 先记录需要保留的人工修改。
2. 点击“保存全部草稿”。
3. 阅读成功或部分失败提示。
4. 逐个切换四个模式，确认 dirty 状态是否消失。
5. 检查授权列表和当前模式角色是否与预期一致。
6. 只有目标模式已保存且不是当前模式时，才执行启用。

保存全部不会替你选择要启用的模式。

## 7.3 409 冲突怎么处理

409 通常表示 `expectedRevision` 与 Host 当前版本不一致：另一个窗口、另一个会话或配置文件已经先修改了同一份数据。

正确顺序：

1. 停止连续点击保存或启用。
2. 让页面重新读取 Host 最新 stored 配置。
3. 对比最新 stored 与自己的未保存 draft。
4. 手动决定保留、合并或放弃哪些字段。
5. 确认后重新保存；需要切换时再启用。

“保存全部”的模式冲突路径会刷新 stored 快照，设计上尽量保留未保存草稿供再次核对；但这不是自动三方合并，也不保证你的草稿应当覆盖别人的新修改。不要因为第二次可能成功就跳过差异检查。

## 7.4 启用失败的校验清单

启用比草稿保存严格。根据错误逐项处理：

| 错误/现象 | 原因 | 处理 |
| --- | --- | --- |
| Lead 模型未配置 | 当前草稿没有 Lead | 选择精确 Lead 路由后保存 |
| Lead 或被引用路线未获授权 | 路由不在共享授权中 | 添加相同 `provider/model`，或改选已授权路线 |
| 启用角色缺少主用路线 | 标准角色已启用但 primary 为空 | 配置主用路线，或明确禁用该角色 |
| fixed 未提供固定档位 | 选择固定推理却没有档位 | 选实际支持的档位，或改用模型默认 |
| smart 没有映射 | 智能映射为空 | 至少配置有效映射，或改用默认/固定 |
| 能力未检测或已过期 | 非 default 推理无法验证 | 刷新能力元数据，再检查声明档位 |
| 档位不在声明列表 | 当前模型不支持该 effort | 选择声明中的档位，不猜枚举 |
| 启用按钮不可点击 | 当前有 dirty、正在保存，或该模式已启用 | 先保存/等待；已启用无需重复点击 |

刷新能力只更新目录元数据。若刷新后仍失败，再做受控连接测试或检查账号权限。

## 7.5 常见故障排查表

### 保存按钮不可点击

当前模式没有未保存修改，或另一个保存操作正在进行。若你修改的是其他模式，先切到该模式查看 dirty；若只改了共享授权，使用“保存全部草稿”。

### 提示全局配置加载失败

全局 enabled 或 revision 尚未成功读取时，页面不会假装全局保存成功。先重新加载设置并检查 Host；不要反复提交草稿期待绕过全局版本检查。

### 保存全部显示“部分完成（N）”

N 是本次记录到的失败数，不是尚未保存的模式总数。检查：

- 哪些模式仍有 dirty；
- 是否出现 409；
- 全局授权是否仍为待同步；
- 当前模式角色是否与刚保存的模式一致；
- Host 是否在线、页面是否已刷新到最新版本。

### 配置已保存，但旧会话行为没变

这是正常的会话快照边界。检查：

- 目标模式是否真正“启用”，而不只是保存；
- 新会话是否在启用之后创建；
- 当前会话是否仍持有创建时的 activeSnapshot；
- 你观察的是主会话模型，还是 role_subagent 的角色路由。

不要用切换设置页或切换聊天标签代替新建会话。

### 角色没有按预期派发

依次检查：

1. 是否实际通过插件的 `role_subagent` 入口调用；
2. 是否传入了正确 roleId；
3. tier 是否明确为 primary、backup 或 upgrade；
4. 是否存在 override 或合法 teamRole 覆盖；
5. 当前会话是否允许该精确路由；
6. 角色是否启用、privacy 是否拒绝外部路由；
7. 该路由能力、权限、额度是否真实可用。

插件不会仅在主用模型失败时自动改走 backup/upgrade。

### 原生 subagent 没有使用插件角色映射

这是入口边界，不一定是故障。插件只接管 `role_subagent`；Host 原生 subagent、fork、显式后端调用不会自动改道到插件。不要让两套入口互相假设。

### 模型能下拉选择，但调用失败

下拉选项只证明目录或配置引用了该模型。继续区分：

- 是否已授权；
- 是否真实连接成功；
- 账号是否有该模型权限；
- 是否限流或额度不足；
- 是否支持所选调用的输入模态与思考档位。

同名模型在不同 provider 下是不同路由，不能互相替代证明。

### 一键配置/推荐失败

先按第六章区分提交失败、轮询失败、任务超时、任务不存在和模型权限错误。保留 jobId 与底层原因，不要把所有错误都当成“网络不好”，也不要在超时后立即重复生成。

### 插件更新后仍看到旧界面或旧版本

安装包版本、当前加载的后端模块和浏览器客户端可能不同步。先核对：

- 已安装并启用的包版本；
- `/modes` 实际返回的后端版本；
- 页面是否重新加载了最新客户端；
- 是否需要按部署流程完整重启应用。

不要仅凭目录中的 package.json 或更新日志标题就宣称运行时已升级。

## 7.6 建议保留的排查证据

- 当前模式 ID、选中模式 ID、dirty 状态；
- 全局角色 revision 与目标模式 revision；
- 失败操作的按钮名称和发生顺序；
- 精确 `provider/model`、tier、reasoningPolicy/effort；
- AI 的 jobId、错误类别和底层 message；
- Host 实际版本与页面显示版本；
- 新会话创建时间与启用时间的先后。

不要提交访问令牌、完整认证头或私密会话内容作为排查证据。
