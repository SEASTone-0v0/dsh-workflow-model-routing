第 1 章　阅读指南与快速开始


1.1 这套系统解决什么问题


这套配置把四件容易混淆的事分开：
1. 主会话默认模型：今后新主会话默认使用哪条模型路线。 2. 专业角色路线：调用 `role_subagent` 时，coder、researcher 等角色使用哪条路线。 3. 授权范围：哪些 `provider/model` 明确允许用于子代理与 AI 配置。 4. 协作过程：任务如何拆分、认领、执行、回传和验收；共享任务记录本身不会启动 Agent。
它不接管所有模型请求，也不会因为页面里写了一个角色，就在后台自动创建该角色。

1.2 打开配置入口


在当前 DeepSeek Harness 桌面应用中：
1. 点击左下角账户区域。 2. 点击「设置」。 3. 在设置左侧选择「运行模式与团队路由」。 4. 页面顶部先选「经济 / 普通 / 性能 / 穷鬼」之一，再进入三个主模块之一。
当前实际渲染的三个主模块是：
模块在这里做什么不在这里做什么 --------- 主会话与派工控制设置 Lead 默认路线、插件派工入口、插件并发不重复编辑四个协作身份；不拦截全部原生工具 模型与角色中心编辑专业角色；高级区设置协作身份覆盖与协作建议不把角色名称当成自动运行的 Agent 模型配置管理授权、能力、分层、连接测试和 AI 草稿不把目录可见或市场推荐当成已验证可用
源码中的 `子代理配置`、`授权模型` 属于保留的旧文案；当前主导航不要按五个并列页面理解。

1.3 第一次使用：最短安全路径


场景 A：只调整今后主会话的默认模型


1. 选择目标模式。 2. 进入「主会话与派工控制」。 3. 在「Lead 主模型」选择已授权路线。 4. 推理政策不确定时选「模型默认」，不要猜档位。 5. 点击「保存设置」。 6. 检查草稿已保存，再点击「启用该模式」。
启用会改变当前模式、活动快照和今后主会话的 Lead 默认选择；不会据此承诺当前已打开会话立刻换模型。

场景 B：让 coder 使用固定角色路线


1. 在「模型配置」中确认目标模型已授权。 2. 进入「模型与角色中心」，找到「代码执行员 · coder」。 3. 确认「启用该角色」已勾选，设置「主用」路线。 4. 备用、升级可留空；它们不是自动故障切换。 5. 保存并启用目标模式。 6. 在当前 Agent 确实提供 `role_subagent` 时，用 `roleId="coder"` 和完整 `prompt` 派发；否则使用原生工具并明确模型参数，不能假定角色表自动生效。

场景 C：只整理一份材料，不需要团队协作


直接在当前会话完成即可。简单任务不要为了“用完角色”而派生多个 Agent；角色是可选分工，不是必须使用的工作流。

1.4 四个模式怎样理解


模式使用意图选择边界 --------- 经济GPT 不可用或额度不足时，优先高质量、成本可控的国产模型是偏好，不禁止其他已授权模型 普通质量、速度、成本均衡不保证固定供应商或固定价格 性能复杂任务和质量优先，可采用更高推理与独立复核不等于自动升级或自动多开 穷鬼极限节约，优先低开销路线是偏好，不再硬禁某供应商或模型
四套模式各自保存 Lead、角色、团队覆盖与任务目标草稿；授权列表是全局共享的，不是每套模式各有一份。

1.5 必须先分清的四个名称


名称实际含义常见误解 --------- 当前主模型当前这次会话实际运行的模型以为它会随说明书下拉框改变 模式 Lead启用模式后写入的今后主会话默认路线以为它就是每个子代理的模型 `roleId=lead`可委派的“总协调员”专业角色以为它会自动成为整棵 Agent 树的 root `teamRole`planner / executor / reviewer / advisor 的显式覆盖槽以为页面保存后就有四个常驻 Agent

1.6 三条最重要的安全规则


- 保存不等于启用：先保存草稿，再明确启用；AI 生成也只进入草稿。 - 目录可见不等于可用：授权、订阅权限、连接状态、输入模态和推理档位分别核验。 - 记录不等于执行：创建任务、启动子代理、任务显示完成、业务验收通过是四个不同事件。

1.7 本说明书的证据范围


说明书依据当前 v2.6.4 源码、真实保存配置的只读快照与已完成的界面/回归证据编写。示例中的 SSS、A/B/C、A1/A2/A3 是讲解任务，不代表这些业务任务真实执行过。具体路线可能随用户后续配置改变，不能把说明书里的模型示例当成永久推荐或当前会话快照。

第 2 章　主会话与派工控制


本章只讲第一个主模块：Lead 默认路线、插件派工入口和插件并发。协作身份覆盖、协作建议已移到「模型与角色中心」的高级区域。

2.1 Lead 主模型


作用


这里设置的是当前模式中的 Lead 配置。模式成功启用后，它会作为今后主会话的默认模型路线；它不是“当前页面正在运行的模型”的实时显示器。

操作


1. 在「Lead 主模型」下拉框中选择 `provider / model`。 2. 设置固定推理档位，或选择「模型默认」。 3. 点击「保存设置」。 4. 若希望应用为当前模式并更新今后默认选择，再点击「启用该模式」。
「模型默认」优先；只有用户明确选择固定档位时才向下游传递固定 `reasoningEffort`。不要把 smartMap 的自动分档文字理解为这里已经实现的动态调度。

可选项从哪里来


下拉框来自当前已授权模型与可用目录。v2.6.3 起，`-vision` 派生别名不在这里展示；原生支持图像输入的非 vision 模型仍可显示。模型名称是否出现在目录里，不代表订阅一定有权访问。

不做什么


- 不在打开设置页时修改当前会话模型。 - 不在保存草稿时修改主会话默认选择。 - 不保证当前已存在会话立即换模型。 - 不因为这里的 Lead 选择而自动改变 coder、researcher 等专业角色。

2.2 固定档位与「模型默认」


选择行为建议 --------- 模型默认使用目标模型自己的默认推理政策不确定时首选 固定档位只传目录明确声明支持的档位不猜 `low/high/xhigh` 等枚举 smartMap模式里可保存分档配置，但当前 Lead 应用不会逐任务动态分档当作配置/建议信息，不当作自动调度承诺
切换到推理能力不同的目标路线时，迁移工具会把不兼容配置降为模型默认并给出警告；这不是静默选择另一模型。

2.3 原生 `role_subagent` 派工


「注册 role_subagent 工具」开关


开启后，插件注册角色派工工具。它的工作方式是：
1. 读取当前会话冻结的模式快照。 2. 根据参数和角色表解析路线。 3. 检查授权与能力。 4. 调用 DSH 原生 `subagents.startActivation` 创建子代理。
插件负责角色映射与检查，真正创建 Agent 的是原生 DSH 服务。

开关作用域


关闭它只表示关闭插件的 `role_subagent` 入口，不等于关闭：
- 宿主原生的 `subagent`、`subagent_fork`； - `subagent_claude_code`、`subagent_codex` 等外部后端； - 任务板或定时任务； - 当前 Agent 已经拥有的其他工具。
工具是否实际出现在本轮工具列表，还取决于 Agent preset、Host 配置和运行时能力；仅开启插件开关不保证每个会话都能调用。

适用与不适用


情况推荐方式 ------ 当前有 `role_subagent`，希望按专业角色和模式快照派工使用插件工具 当前只有原生 `subagent`，且需要明确指定 provider/model使用原生工具 需要 Claude Code / Codex 专用后端使用对应外部子代理工具 只是简单问答或小编辑可直接在当前会话完成
没有「任务超过某复杂度就自动从原生切到插件」的全局规则。

2.4 并发派工上限


这是插件 `role_subagent` 的并发预留上限，不是整台机器、所有任务板或所有原生 Agent 的统一上限。

操作


1. 输入正整数上限。 2. 正常建议最多 2 个执行者；复杂任务可按资源调整，但不要默认无限扩张。 3. 保存草稿，按需启用模式。

实际含义


- 插件在创建前预留槽位，结束时释放。 - 达到上限时返回明确错误，不是把任务悄悄排队后宣称已经启动。 - 原生直接派工、其他插件和任务板不共享这个计数器。 - 共享任务记录的 owner、revision、write scope 仍需要单独管理。

写入范围互斥


并发上限为 2 不代表两个执行者可以修改同一文件。任务书仍需列明：
- 目标与输入； - 各自写入路径； - 禁止事项； - 验收命令； - 交付物与升级条件。

2.5 与「启用该模式」的关系


主会话模块本身没有独立的“立即生效”按钮。它随当前模式草稿一起保存，再由模式启用流程处理：
1. 校验授权与推理能力。 2. 设置当前模式和活动快照。 3. 写入今后主会话的 Lead 默认选择。 4. 若默认选择写入失败，恢复先前的 Lead 默认选择并报错。
页面上的「当前模式」标签、下拉框选择和实际启用状态不是一回事；以启用结果为准。

2.6 常见操作示例


只改 Lead，不动角色


进入主会话模块 → 修改 Lead → 保存 → 启用。角色草稿保持不变，启用后角色按模式快照供 `role_subagent` 使用。

只想关闭插件角色入口


取消「注册 role_subagent 工具」→ 保存 → 启用。随后根据当前 Agent 的真实工具列表选择原生派工，不要假设全局都不能再创建子代理。

并发报错


先检查是否已有插件角色子代理占用槽位，再决定是否等待、减少派工或调整上限。不要通过重复点击制造多个相同任务，也不要把任务板创建记录当成正在运行。

第 3 章　模型与角色中心


这里编辑某个模式草稿中的角色路线。角色卡片不是正在运行的 Agent 列表，也不会因为在页面里出现就自动接收任务。

3.1 角色卡片的公共字段


普通角色卡片显示：
- 标题：`角色名称 · roleId`； - 「启用该角色」； - 「删除角色」； - 主用、备用、升级三个路线编辑器。
路线编辑器可以选择不配置、已授权模型，以及模型默认或受支持的固定推理档位。
字段实际含义不是 --------- `roleId``role_subagent` 查找角色的稳定标识当前 Agent 名称或 Host 任务 ID 启用该角色是否允许按这个角色解析路线是否已经有实例在运行 主用 `primary`默认请求层级失败后的必然成功路线 备用 `backup`只有调用方明确传 `tier="backup"` 才使用自动故障转移 升级 `upgrade`只有调用方明确传 `tier="upgrade"` 才使用按复杂度自动升级 删除角色从当前模式草稿删除删除已经创建的 Agent 或全局授权
没有配置所选 tier 的路线时，会返回 `no-route`，不会自动尝试另外两个 tier。

3.2 十四个内置角色怎样分工


`roleId`中文角色典型输入与输出 --------- `lead`总协调员输入目标与约束；输出拆解、协调和聚合结论 `secretary`任务秘书输入获准出云的材料；输出分类、摘要、计划草案 `architect`方案架构师输入需求与现状；输出依赖、契约、验收标准 `researcher`资料研究员输入问题与来源；输出带证据定位的检索与反证 `long-document`长文整理员输入长材料；输出结构化文稿；上下文能力另验 `analyst`数据分析员输入数据与口径；输出计算解释，数值应由工具产生 `editor`文稿编辑员输入文本与修改要求；输出编辑结果 `creative-writer`创意撰稿员输入主题与风格；输出候选文稿，不宣称固定风格排名 `coder`代码执行员输入任务书与仓库；输出实现、测试证据与风险 `multimodal-researcher`图文研究员输入图文材料；输出多模态研究候选，链路另验 `vision`图像解读员输入图片；输出图像理解，关键数字独立核对 `architecture-challenger`方案质疑员输入方案与证据；输出风险、反例和挑战意见 `reviewer`独立审查员输入交付物与验收标准；输出审查证据，不代替业务验收 `privacy-memory`隐私与记忆边界手工或经验证的本地链路；禁止自动云端派发
小任务可由当前 Lead 兼任架构、编辑或审查，不必为了角色齐全而增加调用。

3.3 独立审查员的配对规则


`reviewer` 的 `kind="reviewer"`，卡片显示的是配对，而不是普通主用/备用/升级三栏：
- `authorProviders`：作者模型所属 provider 集合； - `reviewer`：该作者集合对应的审查路线。
它表达“哪类作者由哪条审查路线复核”的配置关系。不要把它理解成：
- 代码会自动识别每个作品的作者并调用 reviewer； - reviewer 完成后业务验收自动通过； - 同模型再跑一次就构成模型异构复核。
当前通用角色解析仍需要调用方明确发起 reviewer 角色任务；配对是否被某调用链自动使用，要由那条链路自己的代码证明。

3.4 隐私角色是硬边界


`privacy-memory` 的 `kind="privacy"`。即使：
- 页面显示为启用； - 给它配置了某条路线； - 该路线已经授权；
通用派工解析仍会返回 `privacy-role`，拒绝自动云端派发。敏感内容应先人工确认出云范围，或使用经过验证的本地工具链。不要通过改 `override` 绕过这个边界。

3.5 添加与删除自定义角色


添加


点击「添加角色」会生成 `custom-1`、`custom-2` 这样的标准角色，默认启用，主用/备用/升级均为空。
当前卡片没有可见的名称或职责编辑输入框。 添加后应配置路线，并用实际生成的 `roleId` 调用；不要根据旧文案假定可以直接在卡片里重命名或编辑 purpose。若需要完整自定义名称/职责编辑，这是后续 UI 改进项，不是现成功能。

删除


删除需要确认，只改变草稿；保存后才写入模式。它不会删除：
- 已经创建的子代理； - 共享任务记录； - 全局授权模型； - 其他模式里的同名角色。

3.6 高级区域 A：协作身份覆盖


展开「协作身份覆盖」可以配置四个 `teamRole` 槽位：
槽位用途 ------ `planner`显式规划身份 `executor`显式执行身份 `reviewer`显式复核身份 `advisor`显式建议身份
只有调用方传入合法的 `teamRole`，且对应槽位配置了路线时，它才参与解析。它不是四个常驻 Agent，也不是共享任务的执行目标。
路线优先级为：
```text 本次任务 override > 显式 teamRole 的有效槽位路线 > 专业角色的 role[tier] ```
专业角色仍然必须存在、启用，且不能是隐私角色；`override` 和 `teamRole` 只覆盖路线，不越过角色安全边界。

3.7 高级区域 B：协作建议


这里可以编辑：
- 「启用协作建议」； - 「建议触发条件」文本； - 顾问路线及推理配置。
这些是建议与条件配置，不是已经运行的自动升级调度器。填写“两次有证据失败后升级”不会自动让 Host 统计失败并切换模型；真正的升级仍需要调用方明确决策和传参。

3.8 一个完整的角色调用例子


```json { "roleId": "coder", "prompt": "目标：修复…；输入：…；只写：…；验收：…；交付：…", "tier": "primary", "teamRole": "executor", "cwd": "D:/project" } ```
解析顺序：如果本次没有 `override`，先看 `executor` 槽位是否有路线；有则使用它，没有则看 coder 的 `primary`。随后检查全局授权、父会话授权和推理能力，再调用原生创建服务。

第 4 章　模型配置：授权、能力、分层与连接测试


「模型配置」管理全局授权草稿和模型元数据，也提供 AI 配置入口。这里的“可见”“授权”“测试通过”是三个不同状态。

4.1 授权是全局共享的


四套模式各自有 Lead、角色和协作配置草稿，但授权列表全局共享。
因此：
- 给经济模式引用的模型添加授权后，其他模式也能在已授权范围内选择它； - 撤销授权前必须检查所有模式的引用； - 保存非当前模式时，也会同步全局授权，但不会把非当前模式的角色提升为实时全局角色。

4.2 添加授权


1. 在授权列表下方的下拉框选择 `provider / model`。 2. 点击「添加授权」。 3. 列表出现新行，只表示授权草稿增加。 4. 点击「保存设置」；如需应用模式，再明确启用。
添加时会按 `provider + model` 检查精确重复。相同模型名但不同 provider 是不同路线，不能因为显示名相似就删除其中一条。

同名模型的优先顺序


在自动修复、AI 候选规范化等适用路径中：
1. 精确模型 ID 优先选择 `kimi-subscription`； 2. 其次选择 `antigravity`； 3. 两组没有精确 ID 时，才考虑同 provider 或其他组； 4. 只有规范化显示名能唯一匹配时才跨模型 ID 修复；有歧义则报告，不盲目替换。
这不妨碍用户手工选择其他已授权的非 vision 路线。优先规则不是供应商禁用规则。

4.3 撤销授权与引用保护


点击某行的「撤销」：
- 如果该路线仍被 Lead、角色、协作身份、顾问或配对引用，页面会阻止撤销并列出引用； - 没有引用时才从授权草稿移除； - 保存后才写入全局配置。
撤销授权不会自动把角色改派到另一个模型，也不会自动选择备用或升级路线。先调整引用，再撤销，是更安全的顺序。

4.4 恢复默认授权


「恢复默认授权」会把授权草稿替换为后端推荐授权集合，不修改角色分配，保存后才生效。
它与「恢复预设」不同：
操作影响 ------ 恢复默认授权替换授权草稿，不改角色 恢复预设恢复当前模式的 Lead、角色、协作等推荐草稿，保留自定义角色，并把引用路线以只增不删方式并入授权
恢复默认授权可能移除你手工添加的授权，因此操作前应核对草稿与引用。

4.5 能力缓存与推理档位


授权表显示能力缓存状态、可用推理档位和默认档位。路线编辑器只应使用目录明确声明的能力。
状态使用方式 ------ 有效且声明 efforts可选择受支持固定档位或模型默认 声明无 efforts只使用模型默认 未知、失效或过期不猜固定档位；先刷新元数据，必要时显式改回模型默认 旧固定档位已不受支持页面提示；不会为了“修复”而静默改写用户草稿
「刷新能力」读取本地/目录元数据并更新能力缓存，不等于真实生成连接测试。

4.6 测试连接


点击「测试连接」会把当前授权和角色提交给验证接口，对相关路线发起最小真实模型请求。
它可能：
- 消耗少量 token； - 产生费用或占用订阅额度； - 暴露权限、凭据、限流、网络或模型访问错误； - 与纯目录刷新得到不同结果。
测试结果只证明当次请求及其输入条件，不保证所有上下文长度、图像输入、工具调用、并发或后续生成质量都合格。未得到用户明确授权时，不要把自动验收脚本变成真实批量调用。

4.7 分层与刷新分层


分层用于展示经济/普通/性能等参考信息，帮助阅读授权列表。它不再决定某供应商能否被选择，也不是自动路由依据。
「刷新分层」更新分层元数据。分层变化不应被解释为：
- 自动撤销授权； - 自动改变角色； - 自动升级或降级模型； - 禁止某供应商。

4.8 授权表各列怎样读

这不是删除图像理解能力：

第 5 章　保存、启用、复制与恢复预设


这一章是防止“看起来改了，实际没生效”或“以为只改草稿，实际启用了模式”的核心章节。

5.1 页面上的三种状态


状态含义会发生写入吗 --------- 选中某模式当前正在查看哪份草稿不会 显示「未保存」草稿或授权与已存配置不同尚未持久化 显示「当前」Host 记录的 `currentModeId`已经启用过，不等于正在编辑
你可以选中普通模式编辑，同时当前模式仍是经济模式。不要因为标签排在同一排就把“选中”当成“启用”。

5.2 保存设置做什么


点击「保存设置」时，按变化内容执行：
1. 当前模式草稿有变化：提交 `modeId`、完整草稿和 `expectedRevision`。 2. 授权有变化：同步全局授权。 3. 保存的是当前模式：同步当前模式角色到实时全局角色存储。 4. 保存的是非当前模式：只同步授权；全局角色仍使用已存当前模式的角色，避免无关草稿覆盖实时配置。
模式保存成功后，对应草稿会更新为服务器返回值。全局同步失败时会显示“模式已保存但全局同步未完成”一类警告，不能把它当成全部成功。

保存不做的事


- 不切换 `currentModeId`。 - 不创建新的活动快照。 - 不把 Lead 写入今后主会话默认选择。 - 不对所有路线做真实连接测试。 - 不保证旧会话改用刚保存的草稿。
保存路径使用 `skipValidation` 以避免把普通保存变成真实探测；严格路线与推理校验是启用阶段的责任。

5.3 启用该模式做什么


「启用该模式」只在草稿干净时允许继续。若有未保存变化，先保存。
启用会：
1. 按已存 revision 做并发检查。 2. 校验被引用路线的授权和推理能力。 3. 设置 `currentModeId`。 4. 创建新的 `activeSnapshot`。 5. 将 Lead 写入今后主会话的默认模型选择。 6. 如果默认选择写入失败，尝试恢复先前的 Lead 默认选择并报告错误。
启用不是“保存按钮的另一种叫法”，它会改变当前模式与今后默认 Lead。

严格校验可能拒绝的情况


- 引用路线未授权； - 固定推理档位不在目标模型声明集合中； - smartMap 含有目标模型不支持的档位； - 模式缺少必要路线； - 配置 revision 已被其他窗口修改。
启用失败时按完整错误逐项修正，不要为了通过校验随意授权不明路线或猜档位。

5.4 活动快照与会话冻结


启用产生的是新的活动配置；会话实际使用还取决于冻结时机：
```text 启用模式 → activeSnapshot 新 Agent/会话首次需要配置 → 冻结自己的会话快照 后续 role_subagent → 优先读取该会话已冻结快照 ```
已有快照不会因为再次保存或启用而被通用 `ensureSessionSnapshot` 自动替换。因此：
- 新配置可影响今后新会话； - 已打开会话可能继续使用旧快照； - 说明书或实时 `/modes` 返回的最新草稿，不等于当前会话冻结快照。
若需要严格核对某会话的路线，应查看该会话自己的运行时证据，而不是只看设置页。

5.5 复制模式


1. 选中目标模式。 2. 在「复制自…」选择来源模式。 3. 确认复制。 4. 检查目标草稿，再保存。
复制内容包括 Lead、协作建议、角色、协作身份覆盖和任务目标配置。它使用来源模式的已存配置，不是来源模式尚未保存的临时编辑；目标原有草稿会被覆盖。
复制不自动启用目标模式，也不等于复制来源的授权列表——授权本来就是全局共享的。

5.6 恢复预设


「恢复预设」针对当前选中的模式：
- Lead、协作建议、协作身份和任务目标恢复为后端推荐预设； - 内置角色按 ID 使用预设版本； - 自定义角色保留； - 预设引用路线以只增不删方式并入授权草稿； - revision 保留，仍需保存。
它不会立即启用，也不会删除现有额外授权。恢复后应逐项检查，因为“推荐预设”不等于当前账户已经验证全部可用。

5.7 保存全部草稿与单模式保存


「模型配置」里的「保存全部草稿(n)」用于 AI 或多模式编辑后的批量保存。它按顺序处理各模式，再同步全局存储；不是跨所有模式的一次原子事务。部分模式成功、部分失败是可能的，必须看每个结果。详细操作见第 7 章。

5.8 revision 冲突怎样处理


出现 409 或“配置已被其他窗口修改”时：
1. 停止重复点击保存。 2. 记录自己尚未保存的关键改动。 3. 让页面重新载入最新配置。 4. 对比后重新应用改动。 5. 再保存或启用。
`expectedRevision` 是防覆盖机制，不是需要绕过的障碍。全局授权冲突与单个模式冲突可能分别出现。

5.9 推荐操作顺序


```text 选模式 → 修改 Lead/角色/授权 → 检查未保存标记 → 保存设置并确认全局同步成功 → 需要时做能力刷新或明确授权的连接测试 → 启用该模式 → 用新会话或运行时证据验证实际路线 ```

- [ ] 能区分选中、未保存和当前模式。 - [ ] 保存非当前模式不会把它的角色覆盖到实时全局角色。 - [ ] 模式保存成功但全局同步失败时，没有宣称全部成功。 - [ ] 启用前草稿已保存，启用后核对当前模式与活动快照。 - [ ] 没有承诺旧会话立即采用新配置。 - [ ] 复制模式使用来源的已存配置，恢复预设只增授权且保留自定义角色。 - [ ] 409 通过重新载入与合并解决，没有盲目重试。

第六章　AI 一键配置与一键推荐


本章只说明“模型配置”里的两个 AI 功能。它们都会真实调用你选择的已授权模型，可能产生订阅额度或 API 费用。

6.1 两项功能有什么区别


功能输入输出是否直接保存/启用 ------------ 一键配置当前目录、授权和模式草稿四个模式的 Lead、角色路由、团队参数等配置草稿否 一键推荐当前目录、授权和角色每个模式、每个角色的候选模型及理由否，也不自动改路由
“一键”表示一次发起整组 AI 工作，不表示无人工审核、无费用或一次点击完成全部保存和启用。

6.2 执行模型怎么选


两张 AI 卡片各自有“执行模型”下拉框，只列当前已授权模型。
- 一键配置和一键推荐可以使用不同执行模型。 - 执行模型只是本次生成配置/建议的 AI，不会因此自动成为 Lead 或角色路由。 - 列表可见、已授权都不保证当前账号有权限、额度或网络可用。 - AI 执行器不能使用插件的视觉别名；视觉角色由真实多模态模型承担。
两张卡片共享忙碌状态。一个 AI 任务尚未结束时，不会同时从本页面发起另一个 AI 任务。

6.3 一键配置的完整操作顺序


1. 先保存并检查现有重要配置；需要时自行备份。 2. 选择本次 AI 执行模型。 3. 点击“一键配置”。按钮显示进行中时，不要连续重复点击。 4. 等待四个模式逐项返回。后端按模式串行执行，单项失败会记录错误并继续其他模式，不自动重试、不静默换模型。 5. 查看每个模式的成功、失败和 warnings。 6. 返回“主会话与派工控制”“模型与角色中心”逐模式检查生成的草稿。 7. 检查“模型配置”是否新增了 AI 结果引用的授权项。 8. 再执行保存、全局保存和启用；这些不是 AI 自动完成的步骤。

成功结果如何合并


- 只有返回成功的模式才进入合并。 - 请求开始时会为四个草稿和授权列表做快照。 - 如果某个模式在 AI 运行期间被你手动编辑，返回时该模式不会被覆盖，并会显示跳过提示。 - AI 结果引用的路由会以精确 `provider/model` 并入当前授权草稿；你在 AI 运行期间新增的授权不会因旧快照被覆盖。 - “新增授权”仍只是页面草稿，必须后续保存才持久化。

部分成功不是全部成功


结果区按模式显示成功或失败。一个模式失败，不代表另外三个模式没有生成；同样，三个成功也不代表失败项可以忽略。不要只看最后一条总提示，要逐项检查。

6.4 一键推荐的结果怎么读


每个模式下按角色列出候选，主要字段如下：
字段含义 ------ `provider / model`精确供应商与模型 ID 本地目录候选来自当前 Host 返回的目录 模型知识候选来自执行模型自身知识，不等于实时市场调研 本机可用当前目录中存在同一路由；仍不代表权限、额度或连接已验证 理由 / 优势 / 注意AI 的建议文本，需要人工复核
重要限制：
- “模型知识”不是联网检索证明，也不是价格、发行状态或账号权限的实时保证。 - 当前推荐结果主要是阅读材料，没有“把此候选一键写入角色”的按钮。 - 要使用候选，需回到授权和角色编辑器手动添加精确路由、检查能力、保存并启用。 - 不要根据相似显示名称猜测供应商或模型 ID。

6.5 异步任务和轮询


点击后，浏览器先向 `/ai/jobs` 提交一次 POST，取得 `jobId`，随后用 GET 查询任务，而不是保持一个长时间生成请求。
- 轮询间隔约 1 秒。 - 页面等待上限为 480 秒。 - 连续临时轮询失败会有限次容忍；达到连续失败上限后报错。 - 同一任务不会因轮询失败而自动再次 POST 生成。 - 后端逐项串行执行，减少同一订阅账号的并发压力。

6.6 超时、无响应和任务丢失


页面等待超时


出现 480 秒超时和 `jobId` 时，只说明页面停止等待；不代表后端任务已取消或失败。不要立即反复生成。先记录 jobId，检查 Host/网络状态，再决定是否重新发起。

无响应 / `no-response`


这通常表示请求没有得到可判定的 HTTP 响应。页面会尽量显示底层网络原因，例如连接拒绝、超时或读取失败。
此时不能简单认定“模型没工作”：请求可能已经到达 Host。先检查后端任务和网络，不要无脑连续点击。

任务不存在 / `gone`


任务句柄已无法查询。当前任务管理不是跨重启的持久工作流，页面也没有完整的“刷新后重新附着旧 jobId”恢复界面。Host 重启、任务被淘汰或句柄失效后，可能需要重新生成；重新生成前应确认旧任务没有继续产生费用。

HTTP、权限、额度与模型错误


这些错误与轮询失败不同，应按显示的错误类别处理：
- 未授权：先在授权草稿中添加精确路由并保存。 - 模型无权限：检查账号套餐、模型权限或换用你明确选择的模型。 - 额度/限流：检查账号状态、并发和供应商限制。 - 思考档位错误：选择该模型实际声明支持的档位。
不要把所有失败都归结为网络，也不要用“目录里能看到”反驳权限错误。

第七章　保存全部草稿、冲突处理与故障排查


7.1 “保存全部草稿”实际保存什么


按钮显示为“保存全部草稿（N）”。N 由未保存的模式数量和待同步的全局授权/全局角色状态组成，不是将要生成的模型请求数，也不代表 N 个模式会被启用。
它按顺序处理：
1. 逐个保存有未保存修改的模式；单项失败后继续尝试其他模式。 2. 如果授权有变化、全局同步仍待完成，或当前模式本身有修改，再保存一次全局角色与授权。 3. 最后汇总失败数量；全部成功才显示完成。
它不是事务。 可能出现：
- 模式 A 已保存，模式 B 冲突失败； - 模式草稿已保存，全局授权/角色保存失败； - 某些模式保存成功，但当前模式仍处于冲突或未保存状态； - 授权已更新，而某个引用它的模式草稿尚未保存成功。
因此“部分完成”必须逐项核对，不能把按钮恢复可点击理解为全部一致。

7.2 推荐的保存顺序


只改当前模式


1. 在底部点击“保存设置”。 2. 检查顶部不再显示当前模式有未保存修改。 3. 如需切换运行状态，再点击“启用此模式”。

同时改了多个模式或授权


1. 先记录需要保留的人工修改。 2. 点击“保存全部草稿”。 3. 阅读成功或部分失败提示。 4. 逐个切换四个模式，确认 dirty 状态是否消失。 5. 检查授权列表和当前模式角色是否与预期一致。 6. 只有目标模式已保存且不是当前模式时，才执行启用。
保存全部不会替你选择要启用的模式。

7.3 409 冲突怎么处理


409 通常表示 `expectedRevision` 与 Host 当前版本不一致：另一个窗口、另一个会话或配置文件已经先修改了同一份数据。
正确顺序：
1. 停止连续点击保存或启用。 2. 让页面重新读取 Host 最新 stored 配置。 3. 对比最新 stored 与自己的未保存 draft。 4. 手动决定保留、合并或放弃哪些字段。 5. 确认后重新保存；需要切换时再启用。
“保存全部”的模式冲突路径会刷新 stored 快照，设计上尽量保留未保存草稿供再次核对；但这不是自动三方合并，也不保证你的草稿应当覆盖别人的新修改。不要因为第二次可能成功就跳过差异检查。

7.4 启用失败的校验清单


启用比草稿保存严格。根据错误逐项处理：
错误/现象原因处理 --------- Lead 模型未配置当前草稿没有 Lead选择精确 Lead 路由后保存 Lead 或被引用路线未获授权路由不在共享授权中添加相同 `provider/model`，或改选已授权路线 启用角色缺少主用路线标准角色已启用但 primary 为空配置主用路线，或明确禁用该角色 fixed 未提供固定档位选择固定推理却没有档位选实际支持的档位，或改用模型默认 smart 没有映射智能映射为空至少配置有效映射，或改用默认/固定 能力未检测或已过期非 default 推理无法验证刷新能力元数据，再检查声明档位 档位不在声明列表当前模型不支持该 effort选择声明中的档位，不猜枚举 启用按钮不可点击当前有 dirty、正在保存，或该模式已启用先保存/等待；已启用无需重复点击
刷新能力只更新目录元数据。若刷新后仍失败，再做受控连接测试或检查账号权限。

7.5 常见故障排查表


保存按钮不可点击


当前模式没有未保存修改，或另一个保存操作正在进行。若你修改的是其他模式，先切到该模式查看 dirty；若只改了共享授权，使用“保存全部草稿”。

提示全局配置加载失败


全局 enabled 或 revision 尚未成功读取时，页面不会假装全局保存成功。先重新加载设置并检查 Host；不要反复提交草稿期待绕过全局版本检查。

保存全部显示“部分完成（N）”


N 是本次记录到的失败数，不是尚未保存的模式总数。检查：
- 哪些模式仍有 dirty； - 是否出现 409； - 全局授权是否仍为待同步； - 当前模式角色是否与刚保存的模式一致； - Host 是否在线、页面是否已刷新到最新版本。

配置已保存，但旧会话行为没变


这是正常的会话快照边界。检查：
- 目标模式是否真正“启用”，而不只是保存； - 新会话是否在启用之后创建； - 当前会话是否仍持有创建时的 activeSnapshot； - 你观察的是主会话模型，还是 role_subagent 的角色路由。
不要用切换设置页或切换聊天标签代替新建会话。

角色没有按预期派发


依次检查：
1. 是否实际通过插件的 `role_subagent` 入口调用； 2. 是否传入了正确 roleId； 3. tier 是否明确为 primary、backup 或 upgrade； 4. 是否存在 override 或合法 teamRole 覆盖； 5. 当前会话是否允许该精确路由； 6. 角色是否启用、privacy 是否拒绝外部路由； 7. 该路由能力、权限、额度是否真实可用。
插件不会仅在主用模型失败时自动改走 backup/upgrade。

原生 subagent 没有使用插件角色映射


这是入口边界，不一定是故障。插件只接管 `role_subagent`；Host 原生 subagent、fork、显式后端调用不会自动改道到插件。不要让两套入口互相假设。

模型能下拉选择，但调用失败


下拉选项只证明目录或配置引用了该模型。继续区分：
- 是否已授权； - 是否真实连接成功； - 账号是否有该模型权限； - 是否限流或额度不足； - 是否支持所选调用的输入模态与思考档位。
同名模型在不同 provider 下是不同路由，不能互相替代证明。

一键配置/推荐失败


先按第六章区分提交失败、轮询失败、任务超时、任务不存在和模型权限错误。保留 jobId 与底层原因，不要把所有错误都当成“网络不好”，也不要在超时后立即重复生成。

插件更新后仍看到旧界面或旧版本


安装包版本、当前加载的后端模块和浏览器客户端可能不同步。先核对：
- 已安装并启用的包版本； - `/modes` 实际返回的后端版本； - 页面是否重新加载了最新客户端； - 是否需要按部署流程完整重启应用。
不要仅凭目录中的 package.json 或更新日志标题就宣称运行时已升级。

7.6 建议保留的排查证据


- 当前模式 ID、选中模式 ID、dirty 状态； - 全局角色 revision 与目标模式 revision； - 失败操作的按钮名称和发生顺序； - 精确 `provider/model`、tier、reasoningPolicy/effort； - AI 的 jobId、错误类别和底层 message； - Host 实际版本与页面显示版本； - 新会话创建时间与启用时间的先后。
不要提交访问令牌、完整认证头或私密会话内容作为排查证据。

第九章　派工、认领、完成通知与最终验收


本章把协作网络中的 SCHED → ROUTE → SPAWN → CLAIM 展开。核心原则是：任务记录、Agent 执行和业务验收是三件不同的事。

9.1 三种状态不要混用


证据能证明什么不能证明什么 --------- Team 任务记录有任务 ID、owner、revision、依赖和状态已创建模型会话，或结果已验收 subagent/childIdHost 已创建一个子 Agent已认领正确任务，或工作成功 完成通知/账本 completed执行者报告结束或显式写回完成文件正确、测试通过、用户目标达成
最终验收由根 Agent 根据原始需求、实际文件、测试结果和未测范围作出，不能由任何单一状态字段代替。

9.2 第一步：SCHED，选择真正就绪的工作


根 Agent 先检查：
- 用户目标和验收标准是否明确； - 上游依赖是否已有成果证据，而不只是“有人说完成”； - 输入材料是否获准使用； - 写入范围是否与其他执行者互斥； - 当前执行容量是否允许新派工； - 这个任务是否值得独立 Agent，而非根 Agent 直接完成。
共享 Team 任务的 `blocked_by` 用来表达依赖和 readiness。它不会自动把复杂 DAG 变成执行引擎，也不会因为任务 ready 就自动启动模型。
SSS、A、A1 是图中的逻辑任务键。共享 Team 任务应以 Host 返回的真实 taskId 为准；逻辑层级可写入标题和说明，不能假定共享任务具有 task_board 那样的 parentId 字段。

9.3 第二步：建立共享任务记录


典型顺序：
1. `team_task_create` 创建未认领任务，写明目标、输入、验收和 write_scopes。 2. `team_task_list` 查看 ready、owner、revision 和阻塞关系。 3. `team_task_get` 在认领或修改前读取最新完整记录。 4. 使用读到的 revision 做 compare-and-set 更新。
创建记录不等于启动执行者。写范围是协作约定和冲突提示，不是文件系统锁，也不是沙箱权限。

9.4 第三步：ROUTE，解析模型路线


如果通过插件 `role_subagent`：
1. 读取当前会话冻结的模式快照。 2. 检查 roleId 是否存在、角色是否启用。 3. privacy 角色拒绝自动云端派发。 4. 依次解析：显式 override → 合法 teamRole 路线 → role[tier]。 5. tier 只接受 primary/backup/upgrade 语义；未指定时使用 primary，无效值不会成为“自动升级”。 6. 检查精确路由授权。 7. 根据 default/fixed/smart 和真实能力声明解析 reasoningEffort。 8. 任一硬校验失败则返回错误，不静默换模型。
直接使用原生 subagent 时，不经过这套角色映射；由原生显式参数和原生默认规则决定。

9.5 第四步：预留插件执行位


在 await Host 创建子 Agent 之前，插件先原子预留一个位置，避免多个同时请求都通过“检查后再计数”的竞态。
- 计数包含正在创建的预留和已经活跃的插件派工。 - 达到 `maxConcurrentWorkers` 时，本次调用直接报“团队并发上限已达”。 - 这不是自动排队器；根 Agent 应等待现有派工结束后，再决定是否重新发起。 - 启动失败或没有 childId 时，预留会释放。 - 子 Agent 结束事件到达后，活跃计数会释放。
该计数只覆盖本插件的 role_subagent，不是 Host 全局并发限制，也不自动限制直接原生 subagent、其他会话或任务板运行。

9.6 第五步：SPAWN，Host 创建子 Agent


插件把已解析的 provider/model/effort、任务 prompt、父 Agent、cwd 等交给原生 `subagents.startActivation`。
Host 仍负责自己的权限、父子关系、深度、容量和启动校验。插件配置不能绕过这些边界。
成功返回 `childId/subagentId` 后，插件记录：
- 角色、tier、routeSource； - 请求的目标 provider/model/effort； - modeId/modeRevision； - parentSessionId 和创建时间。
这是派工观察记录。requested route 不应被冒充为实际流式调用路线；实际模型需要由会话/事件证据补充。

9.7 第六步：CLAIM，执行者认领任务


子 Agent 启动后，应根据任务书主动读取最新任务：
1. `team_task_get` 或 list 找到目标记录。 2. 检查 owner、blocked_by、状态和最新 revision。 3. 用该 revision 调用 claim。 4. CAS 成功后才按任务书执行；认领冲突则停止重复工作并回报。
如果子 Agent 尚未运行、owner 未被通知或任务仍被阻塞，仅改变任务状态不会让它开始工作。需要时使用 `send_message` 明确通知目标 Agent。
“任务状态变化”不会自动结束 wait_agent、不会自动增加收件箱消息，也不会必然启动一个空闲 Agent。

9.8 第七步：执行与工具循环


执行者每轮可能进行：
1. 模型读取当前上下文和任务书； 2. 选择下一个动作； 3. 发出工具请求； 4. Host 做权限和参数校验并真正执行； 5. 工具结果返回模型上下文； 6. 模型继续、修正或报告阻塞。
文件写入必须遵守约定的互斥范围。格式器、脚本和生成器可能覆盖并发修改，所以共享目录不等于可以随意写同一文件。
角色本身不会自主循环；是 Agent 的模型、Host 和工具共同完成执行。

9.9 第八步：PACK，成果回传与任务写回


执行者交付给父 Agent 的内容至少应包括：
- 结论和实际产物路径； - 关键来源或数据依据； - 运行过的测试及结果； - 未测范围、失败与风险； - 需要父 Agent 继续做的集成动作。
共享任务需要按最新 revision 显式 complete 或写回结果摘要。子 Agent 最终回答、完成通知和账本 completed 是不同通道；不要只完成其中一项就宣称另外两项已发生。

9.10 第九步：依赖推进与返工


父 Agent 收到必要成果后：
1. 读取最新任务账本，确认必需输入确实齐备。 2. 检查成果，而不是只看 completed。 3. 选择下一批 ready 工作；有执行位才派工。 4. 如果不通过，记录缺陷、重新打开或新建修复任务、更新依赖并重新验收。
当前配置中的 failureRetryLimit、预算和 writeScopeIsolation 等字段不能当作自动重试、真实计量或沙箱证明。没有“失败后自动 backup/upgrade”的隐含流程。
顾问也是按需派工，会占用执行容量；条件文本不是后台触发器。

9.11 第十步：FINAL，根 Agent 最终验收


根 Agent 在给最终答复前应：
- 等待所有必要执行者完成； - 审查最终 diff 和产物，而非只收摘要； - 运行相关测试或检查真实渲染； - 对照用户原始验收标准逐项打勾； - 明确区分真实执行、模拟测试、静态检查和未测范围； - 汇总文件、主要结果、限制和后续建议。
任务记录 completed、子 Agent 结束、工具返回成功都不能单独替代这一层。

插件的 `agentTeams.createTask` 只对应共享待办账本，不支持把“taskBoard 独立会话”当成角色派工目标。

第十章　端到端配置与协作操作实例


以下案例说明操作顺序，不指定必须购买的供应商或模型。所有路线都从你已经授权、且当前能力目录可用的项目中选择。

10.1 案例一：配置一个可实际派工的基础团队


目标


配置主会话 Lead、一个 coder 和一个 researcher，使新会话能按角色派发编码与研究任务。

操作


1. 进入“设置 → 运行模式与团队路由 → 模型配置”。 2. 只授权你愿意让团队使用的精确 `provider/model`。目录可见不代表订阅可用，必要时先用“连接测试”。 3. 选择要编辑的运行模式，进入“模型与角色中心”。 4. 给 coder 配置 primary；给 researcher 配置 primary。backup/upgrade 没有明确需要时可留空。 5. 检查相应模型的 fixed/default/smart 推理设置。没有可靠档位声明时优先 default，不猜枚举。 6. 进入“主会话与派工控制”，配置 Lead 默认路线；需要时使用 default，而不是手工锁定未知档位。 7. 如果会用插件 `role_subagent`，勾选其启用项。它只启用插件入口，不代表所有原生 subagent 都被禁用。 8. 回到模式工具栏执行“保存全部草稿”，确认保存计数归零或错误已处理。 9. 点击“启用模式”，等待严格校验通过。

验收


- 当前模式 ID 已切换，activeSnapshot 已产生或更新。 - 新建会话后才使用新冻结快照；旧会话继续保留旧快照。 - 派工返回真实 childId，角色账本记录 roleId、tier 和请求路线。 - 子 Agent 完成后，再检查实际文件和测试；不能只看 requested route 或任务 completed。

10.2 案例二：两人并行完成研究与交付


假设插件并发上限为 2，工作包为：
- A：收集证据； - B：分析证据并形成结论； - C：制作最终交付物。

推荐顺序


1. 根 Agent 创建 A、B、C 三条共享任务。 2. B 的 `blocked_by` 包含 A；C 的 `blocked_by` 包含 B。 3. 根 Agent 用 researcher 路线派发 A，保留另一个执行位处理独立工作。 4. A 的执行者认领任务、读取来源、记录证据、显式完成任务并回传摘要。 5. 根 Agent 检查证据质量，确认 A 真已完成，再派 B。 6. B 完成后，根 Agent 检查结论与来源是否一致，再派 C 或自己整合。 7. 最后统一检查文件、链接、数字和未测范围。

错误做法


- 同时启动 A/B/C，让 B/C 在输入尚未存在时猜测结果； - 因为 B 已 ready 就假设 Host 会自动启动 B； - 把“两个并发槽位”理解为“每条任务各自有两个槽位”； - 将 C 的任务状态改为 completed 后，跳过实际交付物检查。

10.3 案例三：经济模式下优先高质量国模


适用情况


GPT 不可用、额度不足，或你希望控制外部高成本调用时。

配置顺序


1. 在“模型配置”中授权你确认可用的国内模型路线；不要删除其他希望保留的授权。 2. 选择“经济模式”，进入“模型与角色中心”。 3. 根据实际能力把高质量国模设为相应角色的 primary；复杂任务仍可保留你认可的 upgrade。 4. 在“主会话与派工控制”选择适合的 Lead 路线和推理策略。 5. 保存全部草稿并启用经济模式。 6. 新会话中先用小任务验证，再逐步扩大使用。

必须理解


“GPT 不可用时优先高质量国模”是配置和推荐偏好，不是供应商封禁，也不是自动额度探测器。
如果已配置的模型真实调用失败，插件不会因为处于经济模式就自动换到另一家；需要根 Agent 根据错误重新派工或由你修改配置。目录元数据刷新也不能替代真实连接测试。

10.4 案例四：SSS 任务的 A/B/C 分层执行


任务书


根 Agent 先把 SSS 写成可验收合同：目标、输入、交付物、来源要求、隐私边界、并发上限和最终检查项。

A：证据与约束


- A1 整理输入和事实； - A2 分析限制、风险和依赖； - A3 汇总可供 B 使用的证据包。
A 的产出不是最终答案，而是 B 可以核验的输入。

B：研究与方案


- B1 分析关键问题； - B2 比较方案并形成决策； - B3 为 C 编写实施规格。
B 只有在所需 A 输入齐备后才启动。若发现证据缺口，应创建返工任务，而不是静默补造事实。

C：交付与验证


- C1 按规格制作交付物； - C2 执行测试和独立检查； - C3 汇总最终答复、文件和限制。
C 完成不等于 SSS 自动完成；根 Agent 仍需最终验收。

并发示例


在最多两个执行者时，可先并行 A1/A2。A1 完成后，如果 A2 仍在运行且 B 只需 A1，可派 B 的相应部分；如果 B 同时依赖 A2，则继续等待。图中的箭头方向、blocked_by 和真实输入共同决定是否可派，不是看到空槽位就启动所有后续任务。

10.5 案例五：使用显式 backup/upgrade


假设 coder 的 primary 失败：
1. 根 Agent 保存错误证据，确认不是任务书或权限问题。 2. 检查 backup 是否已配置、已授权且适合当前任务。 3. 新派工时显式指定 `tier:"backup"`，或经用户同意修改角色配置后再派。 4. 对比新 childId、请求路线和实际执行证据。
不要因为 backup 存在就宣称系统已自动切换。`upgrade` 同理：复杂任务或两次有证据失败只是升级建议条件，真正派发仍需明确动作。

10.6 案例六：处理 409 并发保存冲突


场景：你编辑草稿期间，另一会话保存了配置。
1. 保存或启用返回 revision 不一致时，停止盲目重试。 2. 保留当前草稿，读取最新已保存配置。 3. 对比双方修改了哪些模式、角色、授权和 Lead。 4. 手动合并需要保留的变化。 5. 使用最新 revision 再保存一次；重新检查 dirty 状态和启用校验。
“保存全部草稿”不是事务锁，也不能保证自动解决多人同时编辑。

10.7 案例七：新增自定义角色


1. 在“模型与角色中心”点击添加角色。 2. 系统生成 `custom-N` 和默认职责类型，路由为空。 3. 配置 primary，按需配置 backup/upgrade。 4. 保存并启用后，通过 role_subagent 使用该 roleId。
当前 UI 没有完整的自定义名称/用途文本编辑器；不要把添加按钮描述成可视化角色编辑器。如果确实需要特定名称或职责文本，应通过受控配置流程处理并保留备份，而不是假装界面已经提供这些字段。

10.8 案例八：从截图切换到实际 GUI 验收


静态 DOM 或 jsdom 测试通过后，仍需验证真实窗口：
1. 确认当前 DeepSeek Harness 窗口和实际 GUI URL。 2. 打开设置和三个模块，检查真实按钮、布局及文案。 3. 展开高级区域，检查 teamRole 和 advisor 控件。 4. 只读测试不得点击保存、启用、连接测试或 AI 生成。 5. 如果其他应用抢占焦点，停止坐标操作，不要继续盲点。
测试脚本中的 writes=0/models=0 只覆盖该脚本；真实窗口验收仍要单独记录。版本号、按钮出现和接口可访问也都不等于真实付费生成已验收。

11.4 功能限制总表


路由与模型


- 运行模式只提供策略和配置模板，不限制客户必须选择某家模型。 - 经济模式的国模优先是偏好，不是自动供应商探测或封禁。 - 授权、目录可见、连接成功和生成质量是四个不同验收层级。 - backup/upgrade 不会自动重试；失败后的路线变化需要显式决策。 - 插件隐藏 vision 别名配置入口，不等于禁用 Host 原生图像输入或未来视觉能力。

会话与执行


- 旧会话保留冻结快照；修改配置不是全量即时热更新。 - 插件执行位只统计自身派工，不是全局限流器。 - 达到上限会拒绝本次调用，不自动排队。 - 共享任务 ready/completed 不会自动启动 Agent 或代替验收。 - 同层级、同角色或同执行者标签不证明可以并行。 - write_scopes 是协作提示，不是隔离沙箱。

配置与 AI


- 保存全部草稿是串行写操作，不是跨模式事务。 - 409 需要人工合并，不能盲目反复提交。 - AI 推荐基于执行模型的知识和目录，不是实时市场调查。 - AI 超时后后端可能仍继续；必须用 jobId 查询，避免重复生成。 - 推荐候选没有“一键把全部候选变成角色配置”的隐含按钮。

账本与证据


- 请求路线不自动等于实际路线；实际模型需会话或事件证据。 - 任务状态不自动等于模型会话状态。 - 源 DOM、jsdom、截图、真实 GUI 和真实付费调用分别证明不同事实。 - 发布说明可访问不等于对应后端所有 handler 都已更新。 - 历史测试通过不等于当前运行窗口已验收。
