# 第十章　端到端配置与协作操作实例

以下案例说明操作顺序，不指定必须购买的供应商或模型。所有路线都从你已经授权、且当前能力目录可用的项目中选择。

## 10.1 案例一：配置一个可实际派工的基础团队

### 目标

配置主会话 Lead、一个 coder 和一个 researcher，使新会话能按角色派发编码与研究任务。

### 操作

1. 进入“设置 → 运行模式与团队路由 → 模型配置”。
2. 只授权你愿意让团队使用的精确 `provider/model`。目录可见不代表订阅可用，必要时先用“连接测试”。
3. 选择要编辑的运行模式，进入“模型与角色中心”。
4. 给 coder 配置 primary；给 researcher 配置 primary。backup/upgrade 没有明确需要时可留空。
5. 检查相应模型的 fixed/default/smart 推理设置。没有可靠档位声明时优先 default，不猜枚举。
6. 进入“主会话与派工控制”，配置 Lead 默认路线；需要时使用 default，而不是手工锁定未知档位。
7. 如果会用插件 `role_subagent`，勾选其启用项。它只启用插件入口，不代表所有原生 subagent 都被禁用。
8. 回到模式工具栏执行“保存全部草稿”，确认保存计数归零或错误已处理。
9. 点击“启用模式”，等待严格校验通过。

### 验收

- 当前模式 ID 已切换，activeSnapshot 已产生或更新。
- 新建会话后才使用新冻结快照；旧会话继续保留旧快照。
- 派工返回真实 childId，角色账本记录 roleId、tier 和请求路线。
- 子 Agent 完成后，再检查实际文件和测试；不能只看 requested route 或任务 completed。

## 10.2 案例二：两人并行完成研究与交付

假设插件并发上限为 2，工作包为：

- A：收集证据；
- B：分析证据并形成结论；
- C：制作最终交付物。

### 推荐顺序

1. 根 Agent 创建 A、B、C 三条共享任务。
2. B 的 `blocked_by` 包含 A；C 的 `blocked_by` 包含 B。
3. 根 Agent 用 researcher 路线派发 A，保留另一个执行位处理独立工作。
4. A 的执行者认领任务、读取来源、记录证据、显式完成任务并回传摘要。
5. 根 Agent 检查证据质量，确认 A 真已完成，再派 B。
6. B 完成后，根 Agent 检查结论与来源是否一致，再派 C 或自己整合。
7. 最后统一检查文件、链接、数字和未测范围。

### 错误做法

- 同时启动 A/B/C，让 B/C 在输入尚未存在时猜测结果；
- 因为 B 已 ready 就假设 Host 会自动启动 B；
- 把“两个并发槽位”理解为“每条任务各自有两个槽位”；
- 将 C 的任务状态改为 completed 后，跳过实际交付物检查。

## 10.3 案例三：经济模式下优先高质量国模

### 适用情况

GPT 不可用、额度不足，或你希望控制外部高成本调用时。

### 配置顺序

1. 在“模型配置”中授权你确认可用的国内模型路线；不要删除其他希望保留的授权。
2. 选择“经济模式”，进入“模型与角色中心”。
3. 根据实际能力把高质量国模设为相应角色的 primary；复杂任务仍可保留你认可的 upgrade。
4. 在“主会话与派工控制”选择适合的 Lead 路线和推理策略。
5. 保存全部草稿并启用经济模式。
6. 新会话中先用小任务验证，再逐步扩大使用。

### 必须理解

“GPT 不可用时优先高质量国模”是配置和推荐偏好，不是供应商封禁，也不是自动额度探测器。

如果已配置的模型真实调用失败，插件不会因为处于经济模式就自动换到另一家；需要根 Agent 根据错误重新派工或由你修改配置。目录元数据刷新也不能替代真实连接测试。

## 10.4 案例四：SSS 任务的 A/B/C 分层执行

### 任务书

根 Agent 先把 SSS 写成可验收合同：目标、输入、交付物、来源要求、隐私边界、并发上限和最终检查项。

### A：证据与约束

- A1 整理输入和事实；
- A2 分析限制、风险和依赖；
- A3 汇总可供 B 使用的证据包。

A 的产出不是最终答案，而是 B 可以核验的输入。

### B：研究与方案

- B1 分析关键问题；
- B2 比较方案并形成决策；
- B3 为 C 编写实施规格。

B 只有在所需 A 输入齐备后才启动。若发现证据缺口，应创建返工任务，而不是静默补造事实。

### C：交付与验证

- C1 按规格制作交付物；
- C2 执行测试和独立检查；
- C3 汇总最终答复、文件和限制。

C 完成不等于 SSS 自动完成；根 Agent 仍需最终验收。

### 并发示例

在最多两个执行者时，可先并行 A1/A2。A1 完成后，如果 A2 仍在运行且 B 只需 A1，可派 B 的相应部分；如果 B 同时依赖 A2，则继续等待。图中的箭头方向、blocked_by 和真实输入共同决定是否可派，不是看到空槽位就启动所有后续任务。

## 10.5 案例五：使用显式 backup/upgrade

假设 coder 的 primary 失败：

1. 根 Agent 保存错误证据，确认不是任务书或权限问题。
2. 检查 backup 是否已配置、已授权且适合当前任务。
3. 新派工时显式指定 `tier:"backup"`，或经用户同意修改角色配置后再派。
4. 对比新 childId、请求路线和实际执行证据。

不要因为 backup 存在就宣称系统已自动切换。`upgrade` 同理：复杂任务或两次有证据失败只是升级建议条件，真正派发仍需明确动作。

## 10.6 案例六：处理 409 并发保存冲突

场景：你编辑草稿期间，另一会话保存了配置。

1. 保存或启用返回 revision 不一致时，停止盲目重试。
2. 保留当前草稿，读取最新已保存配置。
3. 对比双方修改了哪些模式、角色、授权和 Lead。
4. 手动合并需要保留的变化。
5. 使用最新 revision 再保存一次；重新检查 dirty 状态和启用校验。

“保存全部草稿”不是事务锁，也不能保证自动解决多人同时编辑。

## 10.7 案例七：新增自定义角色

1. 在“模型与角色中心”点击添加角色。
2. 系统生成 `custom-N` 和默认职责类型，路由为空。
3. 配置 primary，按需配置 backup/upgrade。
4. 保存并启用后，通过 role_subagent 使用该 roleId。

当前 UI 没有完整的自定义名称/用途文本编辑器；不要把添加按钮描述成可视化角色编辑器。如果确实需要特定名称或职责文本，应通过受控配置流程处理并保留备份，而不是假装界面已经提供这些字段。

## 10.8 案例八：从截图切换到实际 GUI 验收

静态 DOM 或 jsdom 测试通过后，仍需验证真实窗口：

1. 确认当前 DeepSeek Harness 窗口和实际 GUI URL。
2. 打开设置和三个模块，检查真实按钮、布局及文案。
3. 展开高级区域，检查 teamRole 和 advisor 控件。
4. 只读测试不得点击保存、启用、连接测试或 AI 生成。
5. 如果其他应用抢占焦点，停止坐标操作，不要继续盲点。

测试脚本中的 writes=0/models=0 只覆盖该脚本；真实窗口验收仍要单独记录。版本号、按钮出现和接口可访问也都不等于真实付费生成已验收。
