# 第 3 章　模型与角色中心

这里编辑**某个模式草稿中的角色路线**。角色卡片不是正在运行的 Agent 列表，也不会因为在页面里出现就自动接收任务。

## 3.1 角色卡片的公共字段

普通角色卡片显示：

- 标题：`角色名称 · roleId`；
- 「启用该角色」；
- 「删除角色」；
- 主用、备用、升级三个路线编辑器。

路线编辑器可以选择不配置、已授权模型，以及模型默认或受支持的固定推理档位。

| 字段 | 实际含义 | 不是 |
| --- | --- | --- |
| `roleId` | `role_subagent` 查找角色的稳定标识 | 当前 Agent 名称或 Host 任务 ID |
| 启用该角色 | 是否允许按这个角色解析路线 | 是否已经有实例在运行 |
| 主用 `primary` | 默认请求层级 | 失败后的必然成功路线 |
| 备用 `backup` | 只有调用方明确传 `tier="backup"` 才使用 | 自动故障转移 |
| 升级 `upgrade` | 只有调用方明确传 `tier="upgrade"` 才使用 | 按复杂度自动升级 |
| 删除角色 | 从当前模式草稿删除 | 删除已经创建的 Agent 或全局授权 |

没有配置所选 tier 的路线时，会返回 `no-route`，不会自动尝试另外两个 tier。

## 3.2 十四个内置角色怎样分工

| `roleId` | 中文角色 | 典型输入与输出 |
| --- | --- | --- |
| `lead` | 总协调员 | 输入目标与约束；输出拆解、协调和聚合结论 |
| `secretary` | 任务秘书 | 输入获准出云的材料；输出分类、摘要、计划草案 |
| `architect` | 方案架构师 | 输入需求与现状；输出依赖、契约、验收标准 |
| `researcher` | 资料研究员 | 输入问题与来源；输出带证据定位的检索与反证 |
| `long-document` | 长文整理员 | 输入长材料；输出结构化文稿；上下文能力另验 |
| `analyst` | 数据分析员 | 输入数据与口径；输出计算解释，数值应由工具产生 |
| `editor` | 文稿编辑员 | 输入文本与修改要求；输出编辑结果 |
| `creative-writer` | 创意撰稿员 | 输入主题与风格；输出候选文稿，不宣称固定风格排名 |
| `coder` | 代码执行员 | 输入任务书与仓库；输出实现、测试证据与风险 |
| `multimodal-researcher` | 图文研究员 | 输入图文材料；输出多模态研究候选，链路另验 |
| `vision` | 图像解读员 | 输入图片；输出图像理解，关键数字独立核对 |
| `architecture-challenger` | 方案质疑员 | 输入方案与证据；输出风险、反例和挑战意见 |
| `reviewer` | 独立审查员 | 输入交付物与验收标准；输出审查证据，不代替业务验收 |
| `privacy-memory` | 隐私与记忆边界 | 手工或经验证的本地链路；禁止自动云端派发 |

小任务可由当前 Lead 兼任架构、编辑或审查，不必为了角色齐全而增加调用。

## 3.3 独立审查员的配对规则

`reviewer` 的 `kind="reviewer"`，卡片显示的是配对，而不是普通主用/备用/升级三栏：

- `authorProviders`：作者模型所属 provider 集合；
- `reviewer`：该作者集合对应的审查路线。

它表达“哪类作者由哪条审查路线复核”的配置关系。不要把它理解成：

- 代码会自动识别每个作品的作者并调用 reviewer；
- reviewer 完成后业务验收自动通过；
- 同模型再跑一次就构成模型异构复核。

当前通用角色解析仍需要调用方明确发起 reviewer 角色任务；配对是否被某调用链自动使用，要由那条链路自己的代码证明。

## 3.4 隐私角色是硬边界

`privacy-memory` 的 `kind="privacy"`。即使：

- 页面显示为启用；
- 给它配置了某条路线；
- 该路线已经授权；

通用派工解析仍会返回 `privacy-role`，拒绝自动云端派发。敏感内容应先人工确认出云范围，或使用经过验证的本地工具链。不要通过改 `override` 绕过这个边界。

## 3.5 添加与删除自定义角色

### 添加

点击「添加角色」会生成 `custom-1`、`custom-2` 这样的标准角色，默认启用，主用/备用/升级均为空。

**当前卡片没有可见的名称或职责编辑输入框。** 添加后应配置路线，并用实际生成的 `roleId` 调用；不要根据旧文案假定可以直接在卡片里重命名或编辑 purpose。若需要完整自定义名称/职责编辑，这是后续 UI 改进项，不是现成功能。

### 删除

删除需要确认，只改变草稿；保存后才写入模式。它不会删除：

- 已经创建的子代理；
- 共享任务记录；
- 全局授权模型；
- 其他模式里的同名角色。

## 3.6 高级区域 A：协作身份覆盖

展开「协作身份覆盖」可以配置四个 `teamRole` 槽位：

| 槽位 | 用途 |
| --- | --- |
| `planner` | 显式规划身份 |
| `executor` | 显式执行身份 |
| `reviewer` | 显式复核身份 |
| `advisor` | 显式建议身份 |

只有调用方传入合法的 `teamRole`，且对应槽位配置了路线时，它才参与解析。它不是四个常驻 Agent，也不是共享任务的执行目标。

路线优先级为：

```text
本次任务 override
  > 显式 teamRole 的有效槽位路线
  > 专业角色的 role[tier]
```

专业角色仍然必须存在、启用，且不能是隐私角色；`override` 和 `teamRole` 只覆盖路线，不越过角色安全边界。

## 3.7 高级区域 B：协作建议

这里可以编辑：

- 「启用协作建议」；
- 「建议触发条件」文本；
- 顾问路线及推理配置。

这些是**建议与条件配置**，不是已经运行的自动升级调度器。填写“两次有证据失败后升级”不会自动让 Host 统计失败并切换模型；真正的升级仍需要调用方明确决策和传参。

## 3.8 一个完整的角色调用例子

```json
{
  "roleId": "coder",
  "prompt": "目标：修复…；输入：…；只写：…；验收：…；交付：…",
  "tier": "primary",
  "teamRole": "executor",
  "cwd": "/path/to/project"
}
```

解析顺序：如果本次没有 `override`，先看 `executor` 槽位是否有路线；有则使用它，没有则看 coder 的 `primary`。随后检查全局授权、父会话授权和推理能力，再调用原生创建服务。
