# 第十一章　字段速查、故障对照与交付检查表

## 11.1 配置字段速查

| 字段/概念 | 正确含义 | 常见误解 |
| --- | --- | --- |
| currentModeId | 当前已启用的模式 | 正在查看或编辑的模式 |
| activeSnapshot | 新会话可冻结的已启用配置快照 | 所有旧会话会立即更新的配置 |
| revision | 防止并发覆盖的版本号 | 模型版本或插件版本 |
| dirty | 草稿与已保存配置存在差异 | 配置已启用或保存失败 |
| authorizedModels | 全局共享的精确 provider/model 授权集合 | 某个模式独立拥有的模型列表 |
| primary/backup/upgrade | 显式选择的角色路线档位 | 失败后自动切换的三级重试链 |
| fixed/default/smart | 固定档位、使用模型默认、按需求映射档位 | 模型真实生成质量的保证 |
| teamRole | 协作身份 override 指定的角色 | 主会话 Lead 或 modeLead |
| override | 单次派工最高优先级的显式路线 | 永久修改角色配置 |
| role[tier] | 角色在指定档位的路由配置 | 一定可成功调用的供应商账号 |
| routeSource | 本次路线来自 override、teamRole 还是 role | 实际流式请求已经完成 |
| requestedModel | 派工请求希望使用的模型 | 已被实际调用证据确认的模型 |
| maxConcurrentWorkers | 插件 role_subagent 的活跃及预留执行位上限 | Host、所有会话和所有工具的全局限额 |
| advisor | 按需咨询配置和建议条件 | 自动运行的后台顾问 |
| blocked_by | 共享任务的前置依赖 | 自动派工或自动完成依赖 |
| owner | 当前任务认领者 | 最终验收者 |
| write_scopes | 建议的写入范围，用于减少冲突 | 文件系统锁或权限沙箱 |

## 11.2 三种“版本”不要混淆

1. **插件版本**：例如文档基线 v2.6.4，用于判断功能和代码是否加载。
2. **配置 revision**：用于 CAS 保存，防止覆盖其他人的修改。
3. **会话冻结快照版本**：决定某一会话实际看到的路由；旧会话不会因插件升级自动重解释。

排查问题时分别记录这三项，不要只截一个“2.6.4”就推断全部状态。

## 11.3 故障对照表

| 现象 | 优先检查 | 正确处理 |
| --- | --- | --- |
| 四个模式名称错位 | 是否加载旧后端或旧客户端；读取接口是否仍保留旧 label | 使用规范 ID 的读取侧修复和新客户端，不能只改 recommendedPresets |
| 按钮写着“保存草稿(2)” | 两个模式草稿未保存，不代表两个模型调用 | 保存全部草稿，逐项处理结果 |
| 保存成功但旧会话行为不变 | 是否只保存未启用；旧会话冻结了旧快照 | 启用目标模式并新建会话验证 |
| 启用被拒绝 | Lead/角色路线是否授权，推理档位是否有能力声明 | 修正配置后重试，不绕过校验 |
| 模型在目录中但调用失败 | 目录只是元数据；检查账号、权限、额度、通道和真实错误 | 做受控连接测试或更换已验证路线，不静默切换 |
| Kimi 授权列表看似重复 | 是否精确 provider/model 相同，还是不同 provider/别名/显示项 | 只合并精确重复，保留不同供应商和用途 |
| AI 一键任务失败 | 先取 jobId 和 status/error，再区分 POST、轮询和模型阶段 | 用原 jobId 查询；不要立即重复 POST 生成 |
| AI 轮询超时 | 前端停止等待不等于后端取消 | 稍后查询原任务，避免重复计费 |
| AI 推荐了路线但没有生效 | 推荐候选与草稿应用是两件事 | 人工评估候选，再修改角色/授权并保存启用 |
| 任务 ready 但没有执行 | ready 不会自动启动 Agent | 检查依赖、执行位、owner，并显式派工或通知 |
| 任务 completed 但结果不对 | completed 可能只是执行者声明 | 根 Agent 重新验收、返工并记录证据 |
| 并发达到上限 | role_subagent 的活跃和预留位置已满 | 等待现有派工结束；不是自动排队 |
| 原生 subagent 没按角色路由 | 原生入口不经过 role_subagent 映射 | 需要角色映射时使用插件入口并检查作用域 |
| teamRole 没生效 | override 可能优先，或 teamRole 无合法路线 | 按 override > teamRole > role[tier] 检查 |
| privacy 派工被拒 | 隐私硬边界生效 | 改用人工或经过验证的本地流程，不尝试云端兜底 |
| 自定义角色名/用途无法编辑 | 当前 UI 没有这些输入框 | 按真实限制处理，不伪造可视化编辑能力 |
| 设置页面与发布说明版本不一致 | Node 模块缓存可能保留旧 handler | 完整重启后再核验实际接口与窗口 |
| 截图坐标操作影响其他窗口 | 焦点被 Chrome 等程序抢走 | 立即停止点击，重新确认目标窗口 |

## 11.4 功能限制总表

### 路由与模型

- 运行模式只提供策略和配置模板，不限制客户必须选择某家模型。
- 经济模式的国模优先是偏好，不是自动供应商探测或封禁。
- 授权、目录可见、连接成功和生成质量是四个不同验收层级。
- backup/upgrade 不会自动重试；失败后的路线变化需要显式决策。
- 插件隐藏 vision 别名配置入口，不等于禁用 Host 原生图像输入或未来视觉能力。

### 会话与执行

- 旧会话保留冻结快照；修改配置不是全量即时热更新。
- 插件执行位只统计自身派工，不是全局限流器。
- 达到上限会拒绝本次调用，不自动排队。
- 共享任务 ready/completed 不会自动启动 Agent 或代替验收。
- 同层级、同角色或同执行者标签不证明可以并行。
- write_scopes 是协作提示，不是隔离沙箱。

### 配置与 AI

- 保存全部草稿是串行写操作，不是跨模式事务。
- 409 需要人工合并，不能盲目反复提交。
- AI 推荐基于执行模型的知识和目录，不是实时市场调查。
- AI 超时后后端可能仍继续；必须用 jobId 查询，避免重复生成。
- 推荐候选没有“一键把全部候选变成角色配置”的隐含按钮。

### 账本与证据

- 请求路线不自动等于实际路线；实际模型需会话或事件证据。
- 任务状态不自动等于模型会话状态。
- 源 DOM、jsdom、截图、真实 GUI 和真实付费调用分别证明不同事实。
- 发布说明可访问不等于对应后端所有 handler 都已更新。
- 历史测试通过不等于当前运行窗口已验收。

## 11.5 配置上线检查表

- [ ] 明确要编辑的模式和当前已启用模式。
- [ ] 全局授权只包含愿意使用的精确路线。
- [ ] 所有已启用标准角色都有合法 primary。
- [ ] Lead 和引用的 backup/upgrade 均已授权。
- [ ] fixed/smart 档位来自当前能力声明。
- [ ] privacy、reviewer 和 teamRole 的含义符合任务要求。
- [ ] 已保存全部需要的草稿，并处理部分失败。
- [ ] 启用时 strict 校验通过。
- [ ] 使用新会话验证冻结快照。
- [ ] 需要角色路由时使用正确入口和 role_subagent 作用域。
- [ ] 最终检查实际产物，而不只看配置和任务状态。
